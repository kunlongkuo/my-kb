# 子代理派工與回報

## 派工方式

主代理在模型工作開始前，用可用的 subagent／collaboration 工具派出專責工作代理。這是使用者對本流程的明確偏好，無須為例行派工再詢問。只執行建立 Skill 的任務時不額外生成模型。

建議任務名稱：`model_<角色代號>`。優先用最小脈絡的獨立派工（例如 `fork_turns="none"`），在任務內提供完整必要資訊；不更換使用者指定模型，也不自訂推理模型等級。不要為避免主對話佔用而另開使用者側邊欄聊天；subagent 與新聊天不是同一功能。

交給子代理的內容：

```text
使用 $hunyuan-browser-3d-animation，先讀 <安裝路徑>/SKILL.md。
原專案：<絕對路徑>
原圖：<絕對路徑與角色代號>
本次動作：<待機、揮手等已指定項目>
輸出：<project>/Codex/<角色與執行版本目錄>
本次授權與限制：<已允許生成、上傳、既有資產替換等具體範圍；未指定付費額度時不要擅自購買>
瀏覽器：<使用者指定者；可用分頁識別若已知；不要傳登入憑證>
由你負責混元網頁、下載、Blender、Mixamo 及驗收。一般進度保持在你的子任務；遇到需要本人登入或授權的新影響，集中回報。
完成時提供產物絕對路徑、實際完成階段、實測時間／觀測區間、動作來源、驗收摘要及剩餘問題。
```

## 資源分工

- 預設一個模型代理處理一個角色或一批有界的小量任務。主代理不逐步轉貼工具輸出，也不在主對話做長時間等待／重複輪詢。
- 多個代理不得同時操作同一分頁、原生視窗、檔案選擇器或 Mixamo 當前角色。即使是不同分頁，同一帳號的「當前角色」仍是共享狀態，Mixamo 工作依序交接。
- 網頁生成可使用服務本身的佇列；同一個瀏覽器操作代理統一排程。只有獨立輸出目錄、互不爭用的檔案處理或驗收才適合再平行分工，遵守可用代理數與記憶體限制。
- 共用本機 GPU／重型 Blender 工作預設排隊，確定資源充足才並行。不要為五個模型盲目開五個完整工作代理。
- 已建立的外部任務先查狀態，再決定續做或重試；每個角色保存 task id／時間／目前階段，防止接續對話時重新消耗生成次數。

## 主對話行為

派工後簡短告知「已交給模型子代理，完成或需要你操作時集中回報」，然後讓使用者繼續其他對話。使用可用的代理狀態／消息通知接回結果；不要保證平台不支援的跨回合背景運作。若需要狀態查詢，使用有界查詢，不將它做成主對話持續輪詢的工作。

子代理最後回報：

- `status`：static_ready／rig_preview_ready／animation_files_ready／validated／needs_user_action／blocked。
- `artifacts`：真正存在且已驗證的檔案或可開啟本機網頁，使用絕對路徑。
- `timing`：生成、傳輸、修整、綁骨、驗收各階段；不明確時給觀測範圍。
- `motion_source`：實際 Mixamo 動作或自行製作，逐段說明。
- `verification`：檔案檢查、重新匯入、完整播放、多角度及尚存瑕疵。
- `next_action`：只有實際阻礙才列需使用者處理的內容；不要要求確認一般測試細節。

主代理依回報核對關鍵產物後集中摘要。`rig_preview_ready` 不能升格成已取得動畫檔；`animation_files_ready` 仍需驗收才列為 `validated`。
